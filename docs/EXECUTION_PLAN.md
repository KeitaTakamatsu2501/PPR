# PPR v0.1 実行計画

計画開始：2026-09-14。確定日：2026-09-15。状態：ユーザーの方針確認済み、実装未着手。

## 1. 到達点

JTSの人格設定を内容と識別子を保ってPPRへ取り込み、音声資産やJTS本体がなくても編集できるようにする。LLMとの設定ワークショップを継承し、同じ人格の保存版をJTS会話・SBT架空SNSの簡易試演で使う。JTS形式へ書き出し、作者の明示操作でJTSへ反映できるようにする。

PPRは人格の編集元。作品の構成作家、出力JSON、台本進行、SNSの返信構造は作品adapter側に置く。人格の文章は試演や書き出しの都合で自動改稿しない。

## 2. 確定した実装方針

- macOS向け、Python 3.14 / Tk 9。既存Tk UIと操作を継承。
- JTSの基本設定、価値観、詳細トピック、人物関係、口調、セリフ例、設定インタビュー、清書確認、自動保存、localeを継承。
- 音声設定は任意のJTS接続情報。PPR人格の作成・保存に必須としない。
- 現在の194カテゴリは初期テンプレート。固有カテゴリや「恒常的な価値境界」も保持。作者が追加・改名・並べ替えできる。
- Bedrock Mantleと、明示選択されたLM Studioを継承。接続エラー時の別providerへの自動切り替えはしない。
- PPRの正規保存、取込原本、JTS書き出し、試演ログを分離。
- 人格の同一性は作者が判断。ハッシュは「同じ設定を使用した証拠」に限る。
- JTSのソース変更・現行構成作家の置換は対象外。

## 3. 今回の対象外

SBT本体、投稿プール、マルチユーザー、ゲームの勝敗・成長・課金・装備、公開SNS接続、TTS推論・音声学習、汎用plugin配布基盤、クラウド同期、Web UI、人格の自動採点、全モデルへの適合保証。

JTSの巨大な台本生成器をPPRへ丸ごと移植しない。PPR内の「JTS会話・簡易試演」は、共通人格を作品別構成作家へ渡す接続を確認する機能である。

## 4. 調査で確認した前提

- PPRは計画作成前には空ディレクトリ。
- JTS HEADは `3a22063eb731c9ea1652b5a54212aee05592b928`。作業ツリーには未コミット変更があり、`character_locale_store.py`等は未追跡。HEADだけから抽出すると機能が欠落する。
- 正規データは固定プロフィールv8と詳細プロフィールv2のペア。4localeを確認。調査時は各locale 29人、詳細トピック1,754件、人物スタンス64件。これは調査記録であり、実装の固定件数にしない。
- 既存loaderはstrip、既定値補完、旧文面の補正、重複整理などを行う。無編集の往復保持には原JSONの保存が必要。
- イオネのスタイル等、JSON外にも人物固有の補助がある。人物由来の補助とJTSの配役規則を区別する。
- `/opt/homebrew/bin/python3.14` でPython 3.14.7 / Tk 9.0 / Tcl 9.0を確認。JTSのpyprojectは別のPython制約なので、そのまま複製しない。

## 5. 作業順序

### E0 — 抽出元の固定と実装土台

依存：なし。

作業：参照元ハッシュを確認し、必要なソースだけをPPR内のローカル抽出スナップショットへ保存する。PPR専用venv、pyproject、起動スクリプト、テスト・lint設定、`.gitignore`を作る。`data/`、取込原本、モデル設定、試演ログ、ローカルキャラデータを追跡対象から外す。サンプルは架空の小さいfixtureとして作る。

成果：`src/ppr/`、`tests/`、`start_ppr.command`、`pyproject.toml`、`scripts/check.py`、`docs/IMPLEMENTATION_STATUS.md`。

完了条件：専用Pythonで空のPPRウィンドウが開く。JTS/MyFriends/音声探索/ネットワークを通常起動時に呼ばない。依存のない型・サービスをimportできる。

### E1 — 人格データと保存・版管理

依存：E0。

作業：実装計画§3のデータモデルとatomicな単一library保存を実装する。persona ID、locale、順序付きトピック、人物関係、任意の接続情報、取込元参照を分ける。revisionは試演・書き出し開始時に現在の保存済み人格から生成する。自動保存の下書きとは分ける。

成果：`domain.py`、`storage.py`、`revisions.py`と対応テスト。

完了条件：音声・モデル接続なしで新規人格を作成、保存、再読込できる。日本語、空白、改行、長文を保つ。名前変更でIDが変わらない。作品設定の変更で人格revisionが変わらない。

### E2 — JTSの無損失取込と書き出し

依存：E1。

作業：固定v8・詳細v2のペアを読み、原bytesとSHA-256を保存する。既存ID、全名簿、全locale、未知フィールド、固定側templatesを保持する。未編集exportは元bytesを再現。編集exportは元JSONの対応箇所のみ更新する。人物固有補助とJTS固有配役の一覧を作る。

成果：`adapters/jts/importer.py`、`exporter.py`、`validation.py`、互換補助資産、取込・書出しテスト。

完了条件：調査対象の実データをPPR内へ読み込み、未編集で全ファイルが一致する。元JTSのハッシュが変わらない。JTS loaderが隔離環境で出力ペアを読める。原本取込の際に既存loaderの自動補正を正本へ反映しない。

### E3 — 既存デスクトップ編集機能の独立化

依存：E1・E2。

作業：既存GUIのリスト、基本設定、トピック、人物関係、locale、編集状態、復旧処理を移す。音声必須とMyFriends副作用を外す。カテゴリ編集、JTS接続情報の任意編集、取込・書き出し画面を追加する。

成果：`ui/app.py`、`editors.py`、`recovery.py`、`jts_exchange.py`。

完了条件：現行操作に相当する編集ができ、音声不在でも保存可能。未送信インタビュー入力等を含む下書き復旧ができる。locale変更で別localeを上書きしない。

### E4 — 独立LLM接続と設定ワークショップ

依存：E1。GUIへの統合はE3後。

作業：小さいprovider interfaceを実装し、JTSの通信・認証・構造化応答処理を必要部分だけ移す。PPR専用のusage記録を用意する。二つのワークショップの質問・清書・対象ID検証・確認後適用を移す。

成果：`llm/`、`workshops/`、`ui/workshops.py`、通信fixtureテスト。

完了条件：Fake providerでインタビューから清書・確認・反映・復旧まで通る。選択providerとmodelが使われる。認証未設定でも手動編集できる。実LLM接続は明示操作でのみ実行する。

### E5 — 共通試演の関節とJTS簡易試演

依存：E1・E4。

作業：実装計画§7の`RehearsalRequest`、`SchemeAdapter`、実行記録、共通表示を実装。JTS用の簡易構成作家と台詞JSON adapterを作る。人格は保存版の読取専用入力とする。

成果：`rehearsal/runner.py`、`contracts.py`、`context.py`、`schemes/jts_dialogue.py`、`ui/rehearsal.py`。

完了条件：二人を選び、短い会話を生成して読める。作者のメモと比較対象を保存できる。構造エラーは失敗として表示する。試演で人格本文を書き換えない。

### E6 — SBT最小試演

依存：E5。

作業：SBT用の構成作家とSNS adapterを追加。根投稿1件＋返信5件を初期値とし、2回の生成で一本のスレッドを作る。既存SBTクラスの価値観は継承しない。両役割で同じ人格revisionを使う。

成果：`schemes/sbt_thread.py`、SBT試演表示、共通の架空シナリオfixture。

完了条件：返信先、投稿者、順序、件数が検証される。人格別の名前・ID分岐なしで複数の人格を使える。勝敗判定・人格強制変更を加えない。

### E7 — JTSへの明示反映

依存：E2・E3。

作業：staging export、全名簿の差分表示、対象ファイルの競合検知、バックアップ、復旧記録、明示反映操作を実装する。実装計画§5の二ファイル更新手順を守る。

成果：`adapters/jts/apply.py`、反映UI、故障注入テスト。

完了条件：複製したJTS配置に反映でき、途中失敗から復旧できる。反映後のbaseline更新により二回目も正常に反映できる。PPR保存ではJTSが変わらない。対象が取込後に編集されていたら競合として反映を止める。新規・変更音声bindingは対象環境で解決できることを確認する。開発中は本番JTSへ反映しない。

### E8 — 統合検証と実GUI確認

依存：E3〜E7。

作業：`ACCEPTANCE.md`の自動項目を実行。JTS不在の作業ディレクトリで独立起動、日本語IME、カテゴリ編集、自動保存、復旧、試演比較を確認する。実データ往復は読み取り専用で行う。実モデルの少数試演は明示的なliveモードで行い、未実施なら記録する。

成果：`docs/VALIDATION_REPORT.md`とローカルの試演ログ。

完了条件：必須の機械的受入が合格。実GUIとlive通信の実施状況が正確に報告されている。作者の判断を勝手に合格扱いしない。

### E9 — 日常利用への引き渡し

依存：E8。

作業：READMEを実際の起動方法、初回取込、編集、試演、JTS書き出し・反映・復旧の手順へ更新する。データ形式、対応版、制限、作者レビュー未実施項目を記録する。

完了条件：ユーザーがPPRを起動し、元JTSを変更せず一人の人格を編集・試演し、書き出し結果を確認できる。実装AIは完了報告を返す。

## 6. 並列実装できる範囲

E1の型とインターフェースが固定された後、JTS adapter（E2/E7）、GUI（E3）、LLM/workshops（E4）を分担できる。E5の接続契約固定後にSBT adapter（E6）を分担する。最終統合と実データ保持の確認には一人の担当を置く。

## 7. 変更判断の原則

新しい必須質問は残っていない。依存ライブラリの小規模な互換修正、関数名、配置は実装者が解決する。仕様の一部が現状ソースと異なる場合は、データ保持とユーザー回答を優先し、理由を進捗文書へ記録する。

ユーザー判断が必要になるのは、承認済み範囲を変える必要がある場合、既存の作者データを失う変換しかできない場合、外部環境の認証等を本人が操作する必要がある場合に限る。影響しない実装は先に進める。
